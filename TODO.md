## 1b. CPU / lag on the 4K laptop (HP Spectre, Intel UHD 620)
Found 2026-11-14. On the map screen the render thread sat in the Mesa driver's `X11GLContext.nMakeCurrent` (51 of 60 stack samples), not in our drawing; each frame costs about the same whatever changed, and cost follows window pixels (a 1280x720 window used half the CPU of the maximized 3840x2016 one) and frames per second. JavaFX flags did not help (tried: vsync off, software pipeline, pulse cap 30, uploading painter, `vblank_mode=0`, DRI3 off, vram hints). So **fewer frames is the only lever**; a rewrite would not change it.

- Measuring tips: `jcmd` cannot attach to a window started with `sg dialout` (start without it for profiling); `javafx.pulseLogger=true` shows the repainted regions; a bench script that launches, opens J-Map and samples `/proc/PID/stat` lives only in the old scratchpad, so rewrite it if needed. Other programs (Chrome) change the numbers by tens of points, so close them first. **More measuring traps (2026-11-14):** `javafx.pulseLogger=true` can crash the render pipeline with a NullPointerException inside JavaFX's own `PrintLogger` after a couple of thousand pulses, after which the window stops drawing and every reading shows 0 pulses / 1% CPU (a thread dump shows the FX thread waiting in `waitForRenderingToComplete` with the renderer idle): use it only in short runs and distrust a zero. CPU % is also unreliable at low load because the cores swing between 400 MHz and 2.8 GHz (the same work reads 2x higher at the low clock): compare **rendered frames per 10 s** first (floor is about 11), CPU % second.

From comparing the suite with N1MM+, DXLab, Log4OM, Wavelog, GridTracker and the portable loggers. We are working on these.
- [ ] **S** **Phone-friendly web client** is built (`WebClientServer`, Setup ▸ Network & sharing ▸ Phone web client; off by default): the hub serves one responsive page and a token-protected JSON interface for the station and rig state, DX spots with the band-open estimate, the recent log and posting a QSO. QSOs typed without a signal wait on the phone and are sent with their real times when the network returns; an id on each stops a retry being logged twice. Tuning the rig from the phone is a second switch, off by default. **The page has been parsed but not yet opened in a browser or on a phone** - try the log form, the offline queue (switch the phone to airplane mode, log, switch back), the spots tab and the token entry. Left: plain HTTP only, so the page does not load offline (a service worker needs HTTPS); reaching it from outside your network is a job for a VPN, not built in; the hub needs a full JDK (the built-in `jdk.httpserver` module).
- [ ] **M** Our own propagation estimate, stage 1 is built (`Propagation`, `PathPropagationView`, in the Propagation drawer): from the solar flux, sunspot number and K index the app already pulls, a MUF and LUF for the path from your station to a call or prefix (the last spot you clicked), shown as a 24-hour by band grid; it says on the panel that it is an estimate. It is a simple model (secant-law MUF from a flux-based foF2, D-layer absorption for the LUF). The spot card has a **Path now** and a **Best time** line, the J-Map dots fade when the band is probably closed and get a green ring when it is likely open (filter switch "Path now"), and the spot lists show a green / amber / grey dot. **Those screens are not yet looked at in the running app.** It now scores itself (`PropagationCheck`): every cluster spot of 1,000 km or more is a path that was open, so the answer for that path is tallied per band and kept between sessions, and the panel shows the running result (click it to start again). It can only count misses, not false alarms. The first reading (November 2026, about 400 paths) found it far too pessimistic above 20 m (10 m: 96% of heard paths called closed), so **stage 2 (2026-11-18)** adds the winter anomaly and the equatorial anomaly to foF2, counts afresh under `propcheck.tally.v2` (stage 1's numbers stay under `propcheck.tally`), and saves every checked path to `~/.j-hub/propcheck/observations.csv` so a later change can be replayed against everything heard (`PropagationCheck.replay`) instead of waiting weeks. **Next: compare the v2 tally with stage 1's after a few weeks**, then tune by replaying. Not built, because they need data we do not have or licence: the ITU-R P.533 foF2 / M3000 coefficient maps (check their licence), sporadic E, grey-line enhancement, polar paths, and the operator's power and antennas; add them one at a time and watch the check.
